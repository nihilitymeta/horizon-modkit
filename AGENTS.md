# Horizon Modkit: Rules for Agents

The modkit is a Lua library for [Horizon](https://playhorizon.dev) mods. A mod declares items, blocks, mobs, goals,
players and commands as classes with callbacks, the way a NeoForge or Fabric mod does, and needs no Rust. It runs
only on Event Horizon ([whos-carmen/horizon](https://github.com/whos-carmen/horizon)), branch `engine-work`, which
adds the Lua runtime. The mod it exists for is
[horizon-parasite-mod](https://github.com/whos-carmen/horizon-parasite-mod).

The person you work for knows modding well but is not a software developer. Say what you did and what it means in
plain words, and ask before anything you can't undo. Don't push without their word.

## The aim

Mod authors haven't started writing yet, so the modkit tries to have every binding, hook and tool a mod will need
before they ask. When you find something a mod can't do yet, say so. Don't work around it in a mod.

## Where things are

| Path | What it holds |
|---|---|
| `scripts/server/modkit/` | the library; mods load it with `require("@modkit")` |
| `types/horizon.d.lua` | the engine's Lua API types, generated by the engine. Never edit it by hand |
| `examples/example_mod/` | one file for each concept; the only example mod (don't make a second) |
| `docs/` | getting started, guides, reference, testing |
| `tools/` | the checks, and the probe mods the in-game checks load |

The folders sit side by side in `~/src`: `horizon` (Event Horizon), `horizon-resources/26.3` (the vanilla data),
`horizon-modkit`, `horizon-parasite-mod`. Event Horizon's `docs/dev-setup.md` sets a machine up that way.

## Modkit or engine?

- **Modkit**, this repository: a nicer shape for something the engine already offers (a class, a callback, a
  helper). Lua only.
- **Engine**, Event Horizon's `engine-work`: anything Lua can't reach yet (a new hook, a new `horizon.*`
  function, a value the runtime doesn't hand over). Event Horizon's `docs/agents.md` says how to work there. After the
  engine change, copy its `docs/api/horizon.d.lua` here as `types/horizon.d.lua`, then add the modkit side.
- Gaps the engine doesn't cover yet are listed in Event Horizon's `docs/lua-bindings.md`, "Not yet: the shapes to come".

## Issue first

A dev feature (a tool for people making mods: an item, a command, a screen that exists only in a dev game) is built
only once it is on the issue list. Draft it with `.github/ISSUE_TEMPLATE/dev-feature.md`, show the draft to the
person, and post it with the label `dev-feature-request` when they agree.

## Check every change

Set `HORIZON=~/src/horizon`, `RESOURCES=~/src/horizon-resources/26.3` and `GAME_DIR` to a scratch folder. The game
must be built in Event Horizon (`target/fast/horizon-client`, `horizon-ctl`, and `target/debug/cargo-horizon-mod`).

| Check | What it proves |
|---|---|
| `tools/check.sh --self-test` | every mod here loads, `luau-lsp analyze` is clean, a broken mod is refused |
| `tools/example-check.sh` | every concept in the example mod works in a running game |
| `tools/stick-check.sh` | the inspect stick works in a game without `--dev-tools`, and is a plain stick in survival |
| `tools/hook-coverage.sh` | every modkit callback is reached from the game |
| `tools/hud-check.sh` | the draw hooks fire and take the probe's draws |
| `tools/docs-check.sh` | links resolve, and each Lua block in the docs is copied exactly from a file that runs |
| `tools/scaffold-check.sh` | a new mod from `cargo horizon-mod new --template lua` builds and runs |

- Run game checks one at a time: two games on one game folder corrupt each other's world and log.
- A failed in-game check can leave the game running. Quit it with the `horizon-ctl ... quit` line the script
  prints before you run another.
- Write your own game drives as bash scripts: zsh does not split a `$CTL` variable into words.
- Judge `luau-lsp analyze` by its exit code, not by its output.

## Facts that cost time before

- `horizon.log` at load is lost, because the log isn't open yet. Log from a hook or a timer.
- `/reload` runs `scripts/server/init.lua` again but keeps the Lua state's globals. `scripts/registry.lua` and
  `scripts/registry/` changes need a restart.
- `right_click_block` (a block's `on_use`) runs once per hand, so a click handler must do nothing the second time.
- A module under `scripts/server/` or `scripts/shared/` needs a `.luaurc` alias named after its folder, and must
  `return` a value.
- 26.3's game rules have new names: `advance_time`, `spawn_mobs`. The old ones are refused.

## Docs

Follow the [GNOME developer documentation style](https://developer.gnome.org/documentation/guidelines/devel-docs.html):
short sentences, second person, sentence-case headings, lists and tables instead of long paragraphs, no "just",
"simply" or "easy". API entries start with a verb ("Gets the…", "Called when…"); this includes `---` comments in
Lua. A guide's code blocks are copied from the example mod, and `tools/docs-check.sh` checks that they still match.
